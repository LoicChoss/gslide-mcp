# Présentation Google Slides depuis un deck type (Péri Slides MCP + Péri Sheets MCP)

Le deck type porte la charte (masters, layouts, décors). On construit **sur une copie vidée** de ce deck, avec ses layouts et les composants chartés du MCP. Les chiffres qui vivent dans un classeur passent par **Péri Sheets MCP** et arrivent dans les slides reliés.

**Pas pour un PowerPoint.** Dès que la demande parle de PowerPoint, de PPT, de .pptx ou de Keynote (un fichier à produire, un fichier joint à reprendre), ni ce skill ni Péri Slides MCP : c'est le skill pptx habituel. Seule exception, l'utilisateur veut explicitement le résultat en Google Slides (« refais ce PowerPoint dans notre template Google Slides »). `export_pres` ne fabrique pas un PowerPoint : il télécharge un deck Google existant quand l'utilisateur le demande.

**Trois règles absolues**

1. **Le deck type est en lecture seule.** Aucun outil d'écriture ne reçoit son id : ni `build_from_outline`, ni `insert_component`, ni `delete_slides`, ni `set_*`. Tout se fait sur une **copie de travail** : celle que crée `clone_deck`, ou celle que l'utilisateur désigne lui-même (« j'ai déjà copié, tu peux modifier », « c'est une copie de mon template, écris dedans »). Dans ce cas on travaille dedans sans recloner ; on le redit en une ligne dans le premier message, et l'URL donnée est la copie, pas le type. Même règle pour un classeur source que l'utilisateur ne demande pas de modifier : on le lit, on écrit dans un autre.
2. **Étapes gated** : validation explicite de l'utilisateur avant l'étape suivante. La pression (« call dans 40 min », « pas de questions ») raccourcit les messages, pas les étapes : un plan de 8 slides tient en 10 lignes et se valide en une réponse.
3. **On n'invente pas la matière.** Chiffres, faits client, résultats, dates et périodes : ils viennent du brief, des documents lus, du classeur désigné ou de `periscope.md`. À défaut, la valeur est écrite `[À CONFIRMER]`, jamais plausible-et-fausse.

Violer la lettre de ces règles, c'est violer leur esprit.

**Quatre modes.** *Création* : URL d'un deck type → tout le parcours 0 → 5. *Reprise* : l'utilisateur donne un deck déjà copié ou déjà produit avec ce skill et demande une modification (ajouter, refaire, corriger des slides, mettre à jour les chiffres d'un bilan) → pas de clone, cadrage réduit à ce qui manque (les layouts se lisent dans le deck : `list_slides` + `list_layouts`, les slides existantes disent lesquels sont en usage ; `list_sheets_charts` dit quels graphiques sont reliés à quel classeur), plan limité aux slides touchées, puis 2 → 5. Les slides qu'on n'a pas à toucher ne bougent pas. *Refonte* : un deck **source** (ancienne charte, autre agence, PowerPoint que l'utilisateur demande explicitement de refaire en Google Slides) à refaire dans une **nouvelle** présentation bâtie sur le deck type → on ne copie pas ses slides, on en réécrit le contenu avec les layouts et les composants (section « Refonte »). Le deck source est en lecture seule comme le type. *Remplissage* : un deck **déjà maquetté** (template client dont les slides sont dessinées : tableaux, blocs de chiffres, textes d'analyse ; bilan du mois dernier) à remplir ou mettre à jour **en gardant ses slides** → ni layouts ni composants : les textes et les cellules se réécrivent en place avec `refill_text`, qui garde le style de chacun (section « Remplir un deck maquetté »).

## Environnement : hébergé ou local

Les deux MCP existent en **connecteurs hébergés** pour l'équipe, nommés **Péri Slides MCP** (outils Slides : `clone_deck`, `insert_component`…) et **Péri Sheets MCP** (outils Sheets : `read_range`, `manage_chart`…), chacun connecté avec son compte Google @periscope.digital, et en **serveurs locaux** chez qui les a installés. Les outils portent les mêmes noms en local et en hébergé ; quelques différences en hébergé :

- **Pas de fichier local.** Le serveur ne voit pas le disque de l'utilisateur : une prop image (`icon`, `logo`, `photo`, `image`, l'`asset` de `draw`) prend un nom du dossier d'assets (`list_assets()`) ou `drive:<id>` d'un fichier Drive, jamais un chemin. Pour une image que l'utilisateur a sur son poste : il la dépose dans le dossier d'assets ou dans son Drive, ou `insert_image_local` avec `image_base64`. `export_pres` renvoie un lien de téléchargement, pas un fichier.
- **Catalogue en lecture seule.** `save_component` et `delete_component` n'existent pas en hébergé, et aucun outil ne modifie le thème `periscope` : le catalogue et la charte évoluent en local, par la personne qui maintient le MCP. Côté Sheets, les outils de suppression (`clear_values`, `delete_sheet`, `delete_dimensions`…) sont désactivés : un outil absent est voulu, on ne le contourne pas.
- **Template et dossier par défaut communs à l'équipe.** En hébergé, ils sont réglés sur le serveur, les mêmes pour tous (en local, chacun les règle dans son extension). `get_defaults()` les donne ; `null` : rien de réglé, on demande l'URL du deck type et le dossier comme avant.
- **Appels en file.** Le serveur sert un nombre limité d'appels à la fois pour toute l'équipe : un appel lent attend son tour, ce n'est pas une panne. Ne pas lancer vingt captures en parallèle.
- **Outils Sheets absents** (Péri Sheets MCP non ajouté ou non connecté) : les graphiques se font en version dessinée, et on le dit dans le plan (« natif Sheets impossible ici : ajoute Péri Sheets MCP dans tes connecteurs pour des graphiques reliés »). Même logique si Péri Slides MCP manque : rien ne se construit, on demande de l'ajouter. Tableaux : `rows` écrites à la main depuis les chiffres fournis.

## 0. Cadrage (un seul message, trois blocs)

Si l'URL du deck type manque : `get_defaults()`. Un `template` réglé (sur le serveur hébergé ou dans l'extension locale) : le dire en une ligne (« je pars du template *title*, la prez sera rangée dans *folder.name* ») et continuer avec lui ; `null` ou `error` : demander l'URL (et relayer l'erreur). Puis, en lecture seule sur le deck type : `list_layouts` et `screenshot_layouts` (planche captionnée). Poser en un message :

1. **La prez** : client, objectif (AO, reco, bilan…), audience, nombre de slides, messages clés, matière disponible (brief, données, docs : les lire). **Les chiffres sont-ils dans un classeur ?** Si oui, son URL, et s'il faut écrire dedans ou dans un classeur à part (par défaut : on lit le sien, on écrit dans un classeur nommé comme le deck). Pour un bilan récurrent, proposer d'office le natif Sheets. S'il existe un **classeur modèle** pour ce type de bilan (onglets et formules prêts), son URL. **Où ranger le deck ?** Proposer le défaut en une ligne : le dossier par défaut de `get_defaults` pour une copie du template par défaut ou un deck neuf, sinon le dossier du deck type pour une copie, Mon Drive pour un deck neuf ; l'utilisateur peut donner un lien de dossier Drive. Le classeur des graphiques ira dans le même dossier que le deck. **Pour un bilan ou un deck qui sera mis à jour** (pas pour un AO ou une reco ponctuels), ajouter trois questions courtes : le deck sera-t-il mis à jour régulièrement (mensuel, trimestriel) ? si oui, on le construit pour `sync_deck` : graphiques reliés, composants nommés, onglet « Liaisons » dans le classeur ; les tableaux gardent-ils le look du deck ou celui du classeur, et leur nombre de lignes ou de colonnes (annonces, campagnes) change-t-il d'une période à l'autre ? d'où viennent les visuels d'annonces (les URL des plateformes expirent : les mettre dans Drive) ?
2. **Le layout des slides de titre / section** et **le layout des slides de contenu** : montrer la planche, proposer un défaut par nom exact tel que renvoyé par `list_layouts` (titre : le layout de couverture ou de section ; contenu : celui qui a un `TITLE` et de la place libre, souvent le plus `used_by_slides`). Les noms sont propres à chaque deck (« Hero », « Texte_Basique04 », « Title_dark + subtitle »…) : ne jamais les deviner.
3. Les réutilisations Periscope pertinentes (voir `periscope.md`) à proposer d'office pour un AO ou une reco.

Si un classeur est donné : `get_spreadsheet` (titres exacts des feuilles) et `read_range` sur les plages utiles **avant** le plan (plusieurs blocs : un seul `read_range` avec `ranges`, jusqu'à 50 plages rendues dans l'ordre demandé, ce qui ménage le quota ; si le connecteur refuse `ranges`, une plage par appel), pour que le plan cite de vrais chiffres. Attendre la réponse. Les deux noms de layouts retenus sont écrits en tête du plan.

## 1. Plan des slides

Appeler `list_assets()` pour connaître les pictos, logos et photos disponibles (noms sans extension : `bolt`, `people`, `screen-demo`…) avant de proposer un `icon`, un `logo` ou une `photo`. Puis appeler `list_components()` **une fois, avant d'écrire le plan** : l'index du catalogue entier, rangé par **intention** (`intents` : faire retenir des chiffres, comparer, répartition, évolution, classer, étapes, structure, constats et recos, personnes, visuels, données, atelier, habillage), avec pour chaque composant son `use` (quand l'utiliser, alternatives proches) et les titres de ses variantes. Pour chaque slide du plan, partir de son intention et lire le `use` de **tous** les candidats de l'intention, pas seulement des noms familiers. En cas de doute, `suggest_components(description="<intention et contenu de la slide>", avoid=[<composants déjà prévus sur les autres slides>])` classe les candidats et propose `less_obvious`, un bon choix moins attendu à considérer avant de trancher. Choisir d'après `use`, pas d'après le nom : `compare_cards` oppose ✗/✓, `team_grid` montre des personnes, des agences partenaires vont dans `logo_grid`. Les composants retenus, `list_components(names=[…])` donne leurs props, leur `example` et leurs **`variants`** : d'autres réglages prêts du même composant, avec `title` (à quoi ça ressemble), `when` (la situation) et `props` (l'appel à copier). Lire les `when` avant de choisir : une `table` a sa variante simple, pictos de canaux, « vs N-1 » et pilules par seuil ; une `card` ses fonds mint / outline / acid / plain ; un `chart_bars` sa version horizontale et sa version « mensuel avec séparateur de période ». Le catalogue visuel (une slide par composant puis une par variante) est le deck `1cPrerkVnlbxs5QtKjlILoBDO-MczFd-WViffUEUfi1E` : y renvoyer l'utilisateur quand il hésite entre deux rendus.

**Graphiques : dessiné ou natif Sheets.** Les composants `chart_*`, `donut`, `pie` dessinent le graphique dans Slides à partir des `props` : rapide, charte garantie, pourcentages sur les parts, mais figé. Un donut ou un camembert dessiné pèse une dizaine d'éléments (quelques arcs + légende), plus des rayons seulement quand aucune part n'atteint 25 %. Leur variante « natif Sheets, relié » (bloc `native` de la variante) construit le même graphique dans un Google Sheets avec **Péri Sheets MCP** et l'embarque relié avec `insert_sheets_chart`. Choisir ainsi :

| Situation | Choix |
|---|---|
| Chiffres déjà dans un classeur, deck récurrent (bilan mensuel), utilisateur qui veut retoucher les données | **natif Sheets** : on change les cellules, `refresh_sheets_charts` met les slides à jour |
| Parts d'un camembert à lire en % sur le graphique | **dessiné** (`donut` / `pie`) : l'API Sheets ne sait pas afficher les % sur les parts |
| Chiffres ponctuels d'un brief, AO, pas de classeur | **dessiné** |
| Péri Sheets MCP absent | **dessiné**, et le dire |

Dans le plan, dire pour chaque graphique lequel des deux et pourquoi ; en natif, indiquer le classeur (celui de l'utilisateur, ou un nouveau nommé comme le deck) et la feuille. **Tableaux** : il n'existe pas de tableau relié dans Slides ; un tableau « depuis le classeur » est inséré une fois avec le composant `table` (avec `name`), puis suivi par `sync_table`, qui réécrit en place les cellules qui changent (la table garde son id, sa place et son look).

Plan numéroté : par slide → titre, objectif, **layout** (titre / contenu / autre layout du deck si un format spécial s'impose, par son nom exact), **composant(s)**, source des chiffres (brief, classeur + plage) et contenu résumé. Un message par slide, ~5 puces max. Itérer jusqu'à validation.

## 2. Rédaction

Contenu définitif slide par slide : titres, textes markdown des placeholders, props des composants **copiées sur la structure de `example` du catalogue ou de la variante retenue** (`variants[k].props` : mêmes clés : `cards`, `items`, `people`, `phases`…, jamais de clé de mémoire). Dans une `table`, les colonnes de la période précédente (« Clics N-1 », « P-1 ») et de variation (« vs N-1 », « Évol. ») sont reconnues sur l'en-tête : nommer les colonnes ainsi suffit, pas de `delta_cols` à calculer. Pour un graphique natif, rédiger aussi les **données du classeur** (une ligne d'en-tête, catégories en première colonne, une série par colonne, formules bienvenues pour les totaux et les variations) : c'est ce que Péri Sheets MCP écrira. Chiffres au format français `12 400`, `+8 %` ; message clé en `==surligné==`. Jamais de tiret cadratin « — » : utiliser « : » ou une virgule. Validation.

## 3. Construction sur la copie vide

1. Création : `clone_deck(src, name="<Client> · <objet> · <AAAA-MM>")` → id `P` et `folder_id` : la copie est rangée dans le dossier choisi au cadrage : par défaut **celui du deck type** (le dossier par défaut pour une copie du template par défaut : `placed: "default_folder"`), sinon `parent_folder_id` (id ou URL du dossier donné). Si le résultat porte `folder_note` (dossier du type en lecture seule ou invisible : copie dans Mon Drive), le dire et proposer `move_to_folder(P, <dossier>)`. Deck neuf sans type : `create_presentation(title, folder=<dossier choisi>)` ; sans `folder`, il naît dans le dossier par défaut s'il est réglé, sinon à la racine de Mon Drive. Puis `list_slides(P)` : noter les ids **de toutes les slides d'origine**. Reprise : `P` = l'URL donnée ; `list_slides(P)` ; les slides à supprimer sont seulement celles que l'utilisateur a nommées (slides d'exemple, slides à refaire).
2. Pour chaque layout retenu qui a plus d'un placeholder : `screenshot_layout(P, layout, annotate=True)` **sur la copie** (l'annotation crée puis supprime une slide temporaire : c'est une écriture). Lire la carte des clés (`TITLE[1]`, `SUBTITLE[0]`…) avant d'écrire le moindre `fills`.
3. `build_from_outline(P, outline=[{layout, fills}, …])` : une seule écriture, tout est résolu avant. Sur une slide à composant ou à graphique, remplir le titre et laisser les autres placeholders vides.
4. `delete_slides(P, <ids à retirer>)` : en création, toutes les slides d'origine, pour que la copie ne contienne que nos slides (l'API accepte 0 slide, mais créer avant de supprimer) ; en reprise, uniquement celles demandées. Vérifier avec `list_slides(P)`. Pour insérer au milieu d'un deck existant : `insertion_index` (0-based) de `build_from_outline`, ou `move_slide` ensuite.
5. Composants, slide par slide : `get_page(P, slide, compact=True)` pour la géométrie du titre et des placeholders vides ; `insert_component` sous le titre (x = gauche du titre, y = bas du titre + 20 pt, width = largeur du titre ou de la zone libre). `list_layouts` donne aussi `content_area` par layout (la zone libre sous le titre, au-dessus du pied de page) : un bon défaut, à croiser avec `get_page` d'une slide réelle puisque la géométrie du layout peut différer de celle des slides. Chaîner avec le `height_pt` renvoyé. Deck destiné à être mis à jour (bilan mensuel) : donner un `name` à chaque composant qui changera (`insert_component(…, name="yt_top")`) : ses éléments prennent des ids lisibles par rôle (`yt_top_table_1`, `yt_top_slot_1`…, listés dans `ids_by_role`), qui serviront à les mettre à jour sans les chercher ; les visuels d'annonces d'un `ad_scoreboard` sont des emplacements d'image qu'on remplit ensuite avec `replace_images`. Supprimer les placeholders restés vides (`delete_elements`) pour éviter les « Cliquez pour ajouter ». Sur fond sombre : `dark: true` ou variant `dark`.
6. **Graphiques natifs Sheets** (Péri Sheets MCP d'abord, Péri Slides MCP ensuite) :
   1. Classeur, **dans le dossier du deck** : celui que l'utilisateur désigne (URL) s'il a accepté qu'on y écrive ; sinon, s'il existe un classeur modèle, `copy_spreadsheet(spreadsheet=<modèle>, title=<nom du deck>, folder=<URL du deck P>)` ; sinon `create_spreadsheet(title=<nom du deck>, folder=<URL du deck P>, sheets: ["bars", "donut", …])`, une feuille par graphique. L'URL du deck suffit dans `folder` : le classeur naît à côté du deck. Le résultat nomme le dossier et prévient que le classeur prend le partage de ce dossier : le relayer quand le dossier est partagé largement (dossier client, personnes externes). **Secours** tant que Péri Sheets MCP n'a pas ces outils (paramètre `folder` refusé, `copy_spreadsheet` absent) : `create_spreadsheet` sans `folder`, puis `move_to_folder(<classeur>, <folder_id du deck>)` côté Péri Slides MCP ; un modèle sans `copy_spreadsheet` se copie à la main dans Drive (Fichier → Créer une copie), le dire à l'utilisateur. Toujours `get_spreadsheet` pour les titres exacts des feuilles : jamais « Sheet1 » ni « Feuille 1 » supposés.
   2. `set_theme` une fois par classeur : `preset: "periscope"` (Barlow, couleurs charte) ou `preset: "periscope_regies"` quand les camemberts sont par régie (accent2 Google, accent3 Meta, accent4 Bing, accent5 Instagram, accent6 GA4). Camemberts et donuts prennent les accents **à partir d'accent2 dans l'ordre des lignes** : écrire les lignes dans l'ordre Google, Meta, Bing, Instagram, GA4. Une régie absente décale les couleurs des suivantes : pour un autre ordre ou une liste incomplète, passer `colors: {accent2: …, accent3: …}` en plus du preset, dans l'ordre des lignes. Un seul thème par classeur, donc un seul ordre pour tous ses camemberts.
   3. `write_values` des données (`input: "typed"` pour que les nombres et les dates soient compris comme si on les tapait ; le serveur refuse d'écraser des cellules non vides sans `overwrite` : lire le refus, ne pas forcer à l'aveugle ; une plage de plusieurs colonnes écrit **toutes** ses cellules, et une chaîne vide `""` efface la cellule : écrire un appel par bloc contigu de cellules qui changent, jamais une plage qui englobe une cellule à garder), puis `format_cells` avec `number_format: "number:#,##0"` (ou `currency:#,##0" €"`) sur les colonnes de valeurs : les étiquettes et l'axe du graphique suivent le format des cellules.
   4. `manage_chart(action: "add", style: "periscope", headers: 1, …)` avec les arguments du bloc `native.sheets.manage_chart` de la variante (type, `domain`, `series` en liste, `series_colors` ou `point_colors` par régie, `data_labels`, `legend: top`, `stacked`, `series_types` + `series_axes` pour un combo, `pie_hole: 0.55` et `legend: right` pour un donut, `width`/`height` 400 × 400 pour un camembert). Noter le `chart_id` renvoyé. La taille du graphique se change avec `manage_chart(action: "move")` : `update` refuse `width` / `height`.
   5. `screenshot_chart(spreadsheet, id)` : regarder le graphique **avant** de l'embarquer (couleurs, étiquettes, légende, format des nombres). Corriger avec `manage_chart(action: "update")` tant qu'il n'est pas propre ; c'est moins cher que de corriger après coup dans la slide. Les combos, que le rendu « Télécharger en PNG » de Google refuse, passent par un rendu Slides côté script : ils se capturent comme les autres. Si `screenshot_chart` échoue quand même (erreur 500 côté Apps Script), ne pas insister : embarquer le graphique puis le vérifier avec `screenshot` sur la slide, et signaler l'erreur dans le retour d'expérience.
   6. Côté Slides : `insert_sheets_chart(P, slide, spreadsheet, chart_id, x_pt, y_pt, width_pt, height_pt)` dans la zone libre ; Google garde les proportions du graphique (600 × 371 px, ratio 1,6 ; 1 pour un camembert) et le recentre dans la boîte : donner à la boîte le même ratio. `list_sheets_charts` pour retrouver les liens, `refresh_sheets_charts(P)` après toute modification du classeur, `transform_element` pour bouger ou redimensionner (le lien tient).
   7. Tableau depuis un classeur : la première fois, `read_range(formatted: true, format: "json")` puis `insert_component(P, slide, "table", {rows: <lignes lues>, header_fill: "ink", total_row: true, …}, name="regies")` ; ensuite, **jamais de suppression-réinsertion** : `sync_table(P, "regies_table_1", <classeur>, <plage nommée ou 'Feuille'!A1:F8>, dry_run=True)` pour voir ce qui change, puis sans `dry_run`. `style` : `slides` (garde le look du deck, défaut), `sheets` (recopie la mise en forme du classeur), `charter` (look du composant `table`). `rows: "fit"` ajoute ou retire des lignes avant la ligne de total ; `columns: "fit"` (table nommée : une colonne par annonce ou par campagne) ajoute ou retire des colonnes et recale les vignettes `<name>_slot_k`. Préférer une plage nommée (`manage_range` côté Sheets) : elle suit les données quand on insère des lignes.
7. **Mise à jour d'un bilan récurrent** (reprise). Nouvelle période = `clone_deck` du deck de la période précédente (les ids sont gardés, l'onglet « Liaisons » sert à toutes les copies ; ne jamais synchroniser l'ancien deck). Écrire les chiffres de la période dans le classeur (Péri Sheets MCP : lire la plage — les blocs de la période et les sources de l'onglet « Liaisons » en un seul `read_range` avec `ranges` —, puis `write_values` avec `overwrite` sur les seules cellules de la période), puis :
   1. `sync_deck(P, dry_run=True)` : montrer le rapport à l'utilisateur (par ligne de l'onglet : `would change` avec l'ancien et le nouveau texte, cellules changées des tableaux, lignes ou colonnes ajoutées, visuels, graphiques à actualiser ; `errors` avec le numéro de ligne à corriger dans l'onglet).
   2. Après accord : `sync_deck(P)` (tableaux, puis visuels et textes, puis actualisation des graphiques reliés).
   3. `screenshot_range` et `overlap_check` ; les textes qui ne sont pas dans l'onglet (titres, `==surligné==` d'analyse) se reprennent à la main avec `refill_text` ou `replace_text(elements=…)`.
   Sans onglet « Liaisons » (deck ancien) : `sync_table` par tableau, `replace_images`, `refill_text`, `refresh_sheets_charts(P)`, et proposer de créer l'onglet pour les périodes suivantes.
8. **Deck mis à jour régulièrement : l'onglet « Liaisons »** (format : `docs/bilan-sync.md` du dépôt gslide-mcp). Une ligne par élément qui suivra le classeur : `type` (texte, tableau, image) | `élément` (l'id, lisible grâce à `name` : `ids_by_role` du retour d'`insert_component`) | `source` (plage nommée de préférence, sinon `'Feuille'!A1:B2` ; pour un texte une cellule, pour une image une cellule qui contient l'URL, un nom d'asset ou `drive:<id>`) | `options` (`delta=inverse` ; `style=sheets; rows=fit; columns=fit` ; `fit=crop`). Avec Péri Sheets MCP : `manage_sheet` (`add`, `Liaisons`), `write_values` (en-tête puis lignes), `manage_range` (`named_range` par bloc source, `data_validation one_of_list` texte / tableau / image sur la colonne A, `protected_range` `warning_only` sur l'onglet). Vérifier avec `sync_deck(P, dry_run=True)` : zéro erreur, tout `unchanged`.
9. Notes orateur si demandées : `set_speaker_notes`.

Quota : 60 écritures par minute et par utilisateur, côté Slides comme côté Sheets. Une erreur 429 se réessaie après une minute, elle ne se contourne pas.

## 4. Contrôle visuel (obligatoire avant de livrer)

`screenshot_range` sur toutes les slides, puis `overlap_check`. Regarder chaque capture : texte coupé ou débordant, composant qui chevauche un décor du layout (tubes, logo, bandeau), placeholder vide visible, couleurs illisibles, graphique relié mal cadré (bandes vides : ratio de la boîte), chiffres du texte différents de ceux du graphique. Corriger (`transform_element`, largeur, props, `delete_elements`), recapturer, jusqu'à propre. L'absence d'erreur API ne dit rien du rendu.

Livrer : URL de la copie et nom de son dossier + liste numérotée des slides + URL du classeur s'il y en a un (même dossier) (« les graphiques des slides 4, 6 et 7 sont reliés à ce classeur : modifier les cellules puis Actualiser dans Slides »). Le deck type n'a pas bougé.

## 5. Retour d'expérience (fin de run)

Après la livraison, un bloc « Améliorations du skill » : ce qui a coincé (erreur d'outil, composant manquant ou mal rendu, layout piège, question de cadrage manquante, option de graphique absente côté Sheets) et une proposition concrète pour chacun : ligne à ajouter aux pièges de `SKILL.md`, matière à ajouter à `periscope.md`, recette de composant à faire entrer au catalogue, correction côté MCP. Une recette se propose en JSON dans la réponse, pour la personne qui maintient le MCP : en hébergé, `save_component` n'existe pas, et en local on ne l'enregistre qu'avec son accord explicite, après `list_components` pour ne pas écraser une recette existante. Attendre l'accord avant de modifier quoi que ce soit.

## Refonte d'un deck existant (mode 3)

Cadrage comme en création (deck type, layouts titre / contenu), plus le deck **source** en lecture seule. Puis :

1. **Mettre les visuels de côté** : demander à l'utilisateur où (un dossier Drive existant, id ou URL, ou laisser l'outil créer « *<titre>* · sources » dans le dossier d'assets), puis `harvest_deck_assets(source, folder=…)`. Les images reviennent avec une `url` stable et une référence `asset: "drive:<id>"` acceptée par toutes les props image (`browser`, `gallery`, `card.icon`, `logo_wall`…) ; une capture de chaque slide source est rangée au même endroit. Les fichiers moissonnés sont partagés en lecture à qui a le lien : pour des visuels client confidentiels, préférer un dossier dédié au client plutôt que le dossier d'assets commun. Les URL d'images de l'API expirent en trente minutes : cette étape vient en premier.
2. **Lire chaque slide source** : `inspect_slide(source, n)` donne le type de placeholder, les paragraphes avec leurs puces, les cellules des tableaux (`rows`, à passer telles quelles à `table`) et les images.
3. **Choisir les composants par bloc** : `suggest_components(source, n)` découpe la slide en blocs (tableau, rangée de chiffres, blocs côte à côte, liste, image, note de source…) avec des candidats classés, la raison, le `use` et les variantes ; `slide_level` propose des alternatives lues dans le vocabulaire (« avant / après » → `before_after`, « équipe » → `team_grid`, « objectifs » → `media_plan`). Ce sont des heuristiques : le titre va dans le placeholder du layout, une slide donne souvent **plusieurs** composants, et un bloc peut mériter un composant qui n'est pas listé. Un graphique source (image d'un export Excel, graphique Sheets) se refait en dessiné ou en natif selon le tableau de l'étape 1 ; ses chiffres se relisent sur la source ou se demandent, ils ne se devinent pas sur l'image. Le plan (étape 1) liste, par slide source, la slide cible, son layout et ses composants.
4. Rédaction, construction et contrôle comme en 2 → 4 : `create_slide_from_layout` ou `build_from_outline`, le titre en placeholder, les composants dans `content_area` en gardant les proportions des `zone` des blocs sources, les visuels par leur `asset` moissonné. Les slides masquées du source (`hidden`) se signalent et s'ignorent sauf accord.

## Remplir un deck maquetté (mode 4)

Le deck est déjà dessiné : ses slides restent, on change les chiffres et les textes. Pas de `build_from_outline`, pas de composant, pas de `delete_slides` sauf demande.

1. **Copie** : `clone_deck` (rangée dans le dossier choisi au cadrage, par défaut celui du template) ou la copie désignée par l'utilisateur. Le template reste en lecture seule.
2. **Carte des blocs**, slide par slide : `inspect_slide(P, n)` (textes, cellules `rows` des tableaux, ids, `runs` d'un bloc qui mélange les styles) ou `get_page(P, slide, compact=True)`, et `screenshot` pour voir où va quoi. Noter les ids des zones à remplir : valeurs de KPI, cellules de tableau, textes d'analyse, visuels, dates, période. Si le deck sera mis à jour chaque mois et que ses ids sont illisibles (`g3f88324cdba_0_17`), proposer `rename_element(P, [{element, new_id}])` pour des ids parlants (`yt_top_table`) : même rendu, même place ; impossible dans un groupe.
3. **Plan de remplissage** (étape gated) : par slide, une ligne par bloc → id, valeur actuelle, nouvelle valeur, source (classeur + plage, brief). `[À CONFIRMER]` pour ce qui manque.
4. **Écriture** : `refill_text(P, edits=[{element, text} | {element, row, column, text}, …])`, un appel par slide ou pour tout le deck. Chaque bloc garde son style ; une cellule vide prend celui de sa colonne. Les variations signées (`+8 %`, `-3,2 pts`) d'une colonne « vs N-1 » / « Évol. » ou d'un bloc déjà signé prennent la couleur de leur signe, apprise dans le deck ; `delta: "inverse"` quand la baisse est une bonne nouvelle (CPC, CPA, coût par don), `delta: false` pour garder la couleur. Un bloc dont les parties ont chacune leur style (KPI : chiffre 30 pt, libellé 11 pt, variation en vert) se remplit run par run : `{element, runs: ["13 100", null, "-2 %", null]}` à la place de `text`, une entrée par run listé par `inspect_slide` (`null` le laisse), chaque run garde sa taille et sa couleur, la variation prend celle de son signe. Un nombre de runs faux est refusé avec la liste. Pas de markdown dans `text` : une partie en gras se reprend ensuite avec `write_text_markdown` sur ce seul bloc. Lignes devenues inégales après remplissage : `resize_table(P, tableau, row_height_pt=…)`.
4b. **Visuels** (top annonces, captures, logos) : `replace_images(P, [{element, source, fit?}])`, avec pour `source` une URL, un nom du dossier d'assets ou `drive:<id>` (`""` remet l'emplacement vide). L'image garde son id, son cadre et sa place ; `fit: "inside"` montre tout le visuel, `"crop"` remplit le cadre. Jamais supprimer puis réinsérer une image.
5. **Mots isolés** dans un texte qu'on garde (un nom de levier, une période) : `replace_text(P, find, replace, elements=[…])` après un `dry_run=True` qui montre toutes les occurrences.
6. **Graphiques** : reliés (`list_sheets_charts`) → écrire le classeur puis `refresh_sheets_charts` ; dessinés → `delete_elements` puis `insert_component` à la même place (géométrie lue avant).
7. Contrôle visuel comme à l'étape 4 : chiffres qui débordent de leur cadre, couleurs de variation, cohérence texte / graphique.
8. Deck qui reviendra chaque période : après `rename_element` pour des ids lisibles, créer l'onglet « Liaisons » (étape 3.8) ; la période suivante tiendra en un `sync_deck`.

## Rationalisations à refuser

| Excuse | Réalité |
|---|---|
| « Pas le temps de valider, je construis direct » | Le plan tient en 10 lignes. Reconstruire 8 slides à côté coûte plus qu'une réponse. |
| « J'écris sur le template, je nettoierai après » | Le template n'est jamais modifié. `clone_deck` d'abord, sauf copie désignée par l'utilisateur. |
| « Il dit que c'est une copie, mais par sécurité je reclone » | Non : une copie désignée est la copie de travail. Recloner crée un deck orphelin et ignore la demande. |
| « Je garde les slides du template dans la copie, l'utilisateur triera » | La copie ne contient que les slides créées. `delete_slides` des ids d'origine. |
| « Les layouts s'appellent Titre et Contenu » | Chaque deck a ses noms. `list_layouts`, et l'utilisateur choisit. |
| « Je mets des chiffres plausibles » | `[À CONFIRMER]`. Un chiffre inventé dans un AO est une faute. |
| « Pas d'erreur API, donc c'est bon » | `screenshot_range` et regarder ; `screenshot_chart` pour un graphique natif. |
| « Je connais les composants, pas besoin de `list_components` » / « `kpi_grid`, `card_grid`, `table`, ça ira » | L'index par intention montre tout le catalogue, les props ne sont que dans `list_components(names=[…])`. L'index avant le plan, le détail avant la rédaction. |
| « Les clés du layout sont sûrement TITLE[0] et SUBTITLE[0] » | L'ordre des placeholders n'est pas l'ordre visuel. `annotate=True` sur la copie. |
| « À partir de ce Google Slides » = « retouche une copie » | Non : nouveau contenu sur les layouts du type. Si doute, demander. |
| « J'exporte aussi un PDF, ça peut servir » | Rien qui n'ait été demandé. |
| « La slide masquée a les chiffres que je cherche » | Masquée = écartée, souvent fausse. Demander avant de s'en servir. |
| « J'écris directement dans son classeur, c'est plus simple » | Seulement s'il l'a dit. Sinon on lit le sien et on écrit dans un classeur nommé comme le deck. |
| « Le refus d'écraser bloque, je passe `overwrite` partout » | Le refus nomme les cellules : les lire, vérifier que ce sont bien celles de la période, puis écraser celles-là. |
| « Le graphique est relié, les chiffres du texte suivront » | Non : titres, cartes KPI et surlignés sont du texte. Les mettre à jour à la main. |
| « Je mets à jour le tableau maquetté avec `set_table_cell` / `write_text_markdown` » | Ils remettent le style par défaut. `refill_text` garde police, graisse, couleur et alignement, et colore les variations selon leur signe. |
| « `refill_text` ne fait pas ce que je veux, je passe par `batch_apply` » | Dire ce qui manque dans le retour d'expérience ; les requêtes brutes contournent les garde-fous (style, index UTF-16). Un bloc à plusieurs tailles ou couleurs se fait avec `runs`, pas en requêtes brutes. |
| « Je supprime l'image et j'en insère une autre au même endroit » | Nouvel id, nouvelle place dans l'empilement, cadre réduit au visuel. `replace_images` garde l'élément. |
| « Je mets à jour le bilan à la main, élément par élément » | S'il a un onglet « Liaisons », c'est `sync_deck` : un appel, rapport d'abord. Sans onglet, le proposer pour les périodes suivantes. |
| « Le dry run est propre, je lance sans montrer le rapport » | Le rapport est ce que l'utilisateur valide : anciens et nouveaux chiffres. Le montrer, puis lancer. |
| « Je remplace ce libellé sur toute la slide » | `replace_text(slides=…)` remplace **partout** sur la slide, analyse comprise. `dry_run=True` d'abord, puis `elements=` sur les seuls blocs visés. |
| « Il manque un outil de suppression / `save_component`, je contourne avec `raw_request` » | Absent en hébergé, c'est voulu. Le dire à l'utilisateur. |
| « Je lui donne le chemin de mon fichier local » | En hébergé, pas de disque partagé : dossier d'assets, `drive:<id>` ou `image_base64`. |

## Pièges connus

- Les clés de placeholders (`SUBTITLE[3]`) suivent l'ordre des éléments du layout, pas l'ordre visuel : `screenshot_layout(P, layout, annotate=True)` sur la copie avant d'écrire des `fills` sur un layout à plusieurs placeholders. Sans `annotate`, `screenshot_layout` et `screenshot_layouts` sont en lecture seule et peuvent viser le deck type.
- Layouts homonymes (decks fusionnés) : l'appel échoue en listant les candidats ; passer `layout_id`.
- Pas de composant sur un layout à décor plein (couverture, intercalaire) sauf demande.
- Pictos du dossier assets : blancs sur transparent ; `card.icon` se teinte seul, `logo_grid` / `logo_wall` demandent `tint: "ink"` sur fond clair. La liste est dans `list_assets()`, pas dans le catalogue des composants. Un asset absent se dépose dans le dossier d'assets Drive (partagé avec le domaine), il ne s'invente pas.
- Tailles de texte : le thème impose 11 pt minimum aux textes et 10 pt aux libellés, sur-titres, légendes et badges (tableaux exemptés). Un `size` plus petit est relevé au rendu ; ne pas chercher à passer dessous, réduire le texte à la place.
- Un composant retourne `height_pt` : l'utiliser pour empiler, ne pas estimer.
- Un placeholder vide est invisible en présentation mais visible en édition : le supprimer.
- Slides masquées (`hidden: true` dans `list_slides` / `inspect_slide`) : elles ne sont pas présentées et sont souvent une version périmée, avec des chiffres faux. Ne jamais s'en inspirer ni les copier sans l'accord de l'utilisateur ; en reprise, les signaler dans le cadrage (« la slide 19 est masquée, je l'ignore ? »). `set_slide_hidden` masque ou réaffiche.
- Format de page : lire `get_presentation(P, fields="pageSize")` (templates Periscope : 960 × 540 pt) avant de positionner à la main.
- Deck à beaucoup de layouts (80 et plus) : `list_layouts` dépasse la taille de sortie et `screenshot_layouts` sans filtre épuise le quota de 60 lectures par minute. Lire le fichier de sortie de `list_layouts` avec un script (nom, id, placeholders, `used_by_slides`), puis appeler `screenshot_layouts` avec une liste de 6 à 8 noms : les layouts en usage dans le deck et les candidats titre / contenu.
- `build_from_outline` crée aussi les placeholders laissés sans `fills`, avec des ids Google aléatoires (`SLIDES_API…`). Avant `delete_elements`, un `get_page(P, slide, compact=True)` par slide pour récupérer ces ids ; les placeholders remplis, eux, portent des ids prévisibles (`<slide_id>_subtitle0`).
- La géométrie du layout n'est pas celle des slides réelles : sur `Texte_Basique04`, le titre fait 272 pt de large dans le layout et 800 pt sur les slides du deck. Avant de remplir, comparer `get_page` d'une slide existante du même layout avec celle du layout. Pour redimensionner, `transform_element(width_pt=…)` ou `height_pt` (une seule dimension garde les proportions, les deux fixent le cadre) ; il déplace aussi, axe par axe (`x_pt` seul garde la hauteur, `dy_pt` seul décale verticalement ; seuls `x_pt` + `dx_pt` ensemble sont refusés).
- Graphiques natifs Sheets, appris en construisant le catalogue : `series` est toujours une liste, même pour une série ; sur un combo, `line_width` / `line_dash` se donnent par série avec `0` pour la série colonne (Google refuse un style de ligne sur une colonne) ; `pie_labels` (légende sur les parts) ne s'affiche pas une fois embarqué dans Slides, prendre `legend: right` ; les pourcentages sur les parts n'existent pas dans l'API (réglage manuel dans l'éditeur Sheets, effacé par tout `manage_chart update`) : garder le `donut` dessiné quand les parts doivent se lire ; les couleurs des parts viennent du thème (accent2…), pas d'une couleur par part ; sans `format_cells` sur les colonnes de valeurs, les étiquettes sortent sans séparateur de milliers.
- Tableaux (`table`) : une ligne ne descend pas sous ~26 pt, quels que soient `row_h`, `size` ou `height_pt` (hauteur minimale imposée par Slides). Compter 26 pt par ligne pour placer un tableau et réserver la place du texte en dessous ; au-delà d'une dizaine de lignes, couper en deux tableaux ou deux slides.
- Graphique combo natif : les étiquettes des barres et de la courbe se chevauchent. Les séparer en montant `axis_max` de l'axe gauche (barres) à environ 2,5 fois la valeur maximale : les barres occupent le bas, la courbe le haut.
- Graphique relié et droits : chacun voit l'image embarquée, mais **Actualiser** (dans Slides ou par `refresh_sheets_charts`) demande l'accès au classeur. Partager le classeur avec les mêmes personnes que le deck ; un graphique d'un classeur supprimé ou non partagé reste figé sur sa dernière image.
- Noms de feuilles : un classeur créé sur un compte en français s'appelle « Feuille 1 », pas « Sheet1 ». Les titres viennent de `get_spreadsheet`, toujours.
- Remplacer une image : `replace_images`, jamais `delete_elements` + `insert_image` ni un `replaceImage` brut. Google réduit l'élément à la nouvelle image (CENTER_INSIDE) et efface son texte alternatif : `replace_images` remet le cadre avant et après. Les URL des plateformes publicitaires expirent : mettre le visuel dans Drive et passer `drive:<id>`.
- `replace_text` limité à des slides remplace toutes les occurrences de ces slides, y compris dans un paragraphe d'analyse qui cite le même mot (vu avec « nouveau levier »). `dry_run=True` liste chaque occurrence (slide, élément, cellule, contexte) sans rien écrire ; puis `elements=[…]` pour ne toucher que les blocs voulus. Pour réécrire un bloc entier : `refill_text`.
- `write_values` (Péri Sheets MCP) sur une plage de plusieurs colonnes écrit chaque cellule du rectangle : un `""` placé pour « sauter » une colonne l'efface. Lire la plage avant, écrire bloc contigu par bloc contigu, relire après.
- Emplacement dans Drive : `clone_deck` range la copie à côté du deck type (une copie du template par défaut va dans le dossier par défaut s'il est réglé) ; `create_presentation(folder=…)`, `create_spreadsheet(folder=…)` et `copy_spreadsheet(folder=…)` rangent où on leur dit (pour un classeur, l'URL du deck suffit). Sans dossier, un deck neuf naît dans le dossier par défaut de Péri Slides MCP s'il est réglé (`get_defaults`), un classeur neuf dans celui de Péri Sheets MCP s'il en a un, sinon tous deux à la racine de Mon Drive ; une copie de classeur reste à côté de l'original. Pour ranger après coup : `move_to_folder` (Péri Slides MCP, tout fichier) ou `move_spreadsheet` (Péri Sheets MCP). Un fichier rangé prend le partage de son dossier. Donner l'emplacement dans la livraison.
- Un deck source à moissonner peut contenir des images minuscules (puces, pictos) : `harvest_deck_assets` les saute (`min_pt`) et les liste dans `skipped` ; ce qui n'est pas une image (vidéos, formes libres, WordArt) n'est pas moissonné, `inspect_slide` le signale.
